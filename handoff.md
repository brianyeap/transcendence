## 1. EXECUTIVE PROJECT OVERVIEW
### 1.1 Product, audience, value proposition
**DUEL** is an authenticated, head-to-head simulated crypto-trading game, not a brokerage or real-money exchange. Two people join the same match, observe the same BTC market candle sequence, and place long or short market orders against virtual starting capital. A fixed countdown leads into a fixed trading window. A long-running Node game server validates orders, maintains each player's net position and balance, marks positions to market, settles outstanding exposure at the last streamed price, and declares the winner by final capital (equal capital is a draw). Completed matches, executions, and streamed candles are persisted for history and statistics. The UI adds a game lobby, profiles, a leaderboard, friends/presence, settings, instructions, and account security. See `docs/prd/trading-game/prd.md` and the implementation in `socket/server.js`, `socket/engine-math.js`, `app/components/duel/`, and `app/matches/[matchId]/`.

The intended users in the PRD are people wanting a quick competitive trading game, beginners practicing direction and sizing, and friends competing in short virtual-market battles. The differentiator is a synchronized, server-authoritative contest rather than a solo price chart: the client can propose trades and display estimated equity but cannot decide fills or winners. There are no deposits, real exchange execution, leverage, order book, fees, stop orders, tournaments, or native mobile app in the documented MVP. `app/login/page.tsx` expressly labels the experience “Simulated markets - No real funds at risk.”

**Current implemented rules override old planning examples:** `lib/match/rules.ts` fixes the match length at **60 seconds**, `app/api/rooms/join/route.ts` fixes pre-match countdown at **10 seconds**, and room creation accepts **5,000 / 10,000 / 20,000** virtual starting capital (`app/api/rooms/route.ts`, `app/components/duel/create-match-modal.tsx`). Room symbol is written as `BTC/USDT`; market acquisition actually calls the Coinbase **BTC-USD** public endpoints (`socket/server.js`). The PRD's 180-second recommendation and references to Binance are proposals, not current settings. The old PRD also proposes Prisma and separate `rooms` and `matches` records; neither matches the current implementation: **one `matches` row is both the waiting room and the game**, and data access uses Supabase JS/PostgREST with checked-in SQL migrations, not Prisma.

### 1.2 Architectural pattern and authority boundaries
This is a **small distributed application / split web-and-realtime service**, not a single-process monolith and not a fleet of independently deployed microservices as evidenced by the repository:

1. **Web / BFF:** Next.js App Router under `app/` serves React Server Components, client components, and a few HTTP route handlers. `proxy.ts` refreshes/validates Supabase cookie sessions and redirects unauthenticated visitors. Server route handlers in `app/api/` apply identity checks for room operations; most profile/history/friends/leaderboard reads instead go directly from a server or browser Supabase client to Supabase, not through an internal API.
2. **Realtime match engine:** a separate CommonJS Node/Express/Socket.IO service in `socket/server.js` listens on port **4000**, authenticates the socket's Supabase token and match membership, owns in-memory live match state, fetches market data, emits lifecycle/tick/score events, validates and executes trades using `socket/engine-math.js`, persists results, and exposes realtime traffic. It is a long-lived process; it is not implemented as a Next.js route.
3. **Managed identity/data:** Supabase Auth handles email/password, Google OAuth, sessions and TOTP MFA; Supabase Postgres stores profiles, matches, player snapshots, candles, trade ledger and friends; Supabase Storage is used by avatar upload. Supabase Row Level Security (RLS) mediates normal browser/server clients. Server-only service-role clients intentionally bypass RLS and require explicit authorization in application code.
4. **Observability:** web and socket export OpenTelemetry metrics over OTLP to a collector configured under `monitoring/`, which exposes Prometheus-format metrics to Prometheus and provisioned Grafana dashboards. This is configured infrastructure, not evidence of a running production telemetry service.

The two primary state planes are **durable database state** (`matches`, `match_players`, `match_candles`, `trades`) and **ephemeral engine state** (`liveMatches` map in `socket/server.js`). The browser's `lib/match/socket-transport.ts` rehydrates from Supabase on page open/reload, then listens over Socket.IO. The browser mirrors formulas for *display-only* unrealised PnL/equity on price ticks; `socket/engine-math.js` and the engine remain the trading/settlement authority. For an accurate handoff, avoid conflating this live match path with the separate, older, default-mock `lib/api/` abstraction; the current `app/matches/[matchId]/match-screen.tsx` uses `lib/match/`.

### 2.2 Persistence, identity, external services and credentials
- **Supabase Postgres + Supabase Auth:** `supabase/migrations/0000_baseline.sql` is the checked-in baseline; `0001_drop_matches_join_policy.sql` removes an unsafe normal-user match UPDATE policy. `supabase/mfa-rls-policy.sql` is an **example**, not a numbered migration. The actual baseline defines `profiles` (id, username, email, timestamps), `matches` (also used as rooms), `match_players`, `match_candles`, `trades`, `friends`; views `friends_with_status` and `public_profiles`; RPC `ping_online`; enums `match_status`, `position_side`, `trade_side`; RLS and foreign keys. Important distinctions: money/price columns are Postgres `numeric` but JS code converts them to `Number` and rounds some calculations to two decimals; there is no Prisma/Redis/cache service. The client-side `lib/api/mock.ts` is an in-memory demo backend, not shared infrastructure.
- **Auth:** `lib/supabase/client.ts` creates the public browser client; `lib/supabase/server.ts` creates a cookie-backed request-scoped server client; `proxy.ts` performs auth redirects; `lib/supabase/admin.ts` builds the service-role client for trusted server routes; the socket engine constructs its own service-role client. `app/login/page.tsx` uses password sign-in/sign-up, profile upsert, and Google OAuth; `app/auth/callback/route.ts` exchanges PKCE code and checks verified MFA factors; `app/auth/verify-mfa/page.tsx` challenges/verifies TOTP. Google sign-in requires provider configuration in Supabase, not demonstrated by checked-in files.
- **Market data:** `socket/server.js` fetches public Coinbase Exchange endpoints `https://api.exchange.coinbase.com/products/BTC-USD/candles?granularity=60` and `/products/BTC-USD/ticker`. It replays prefetched one-minute historic candles every **500 ms** during the one-minute match (rather than consuming a live exchange trading feed); if no candles load, ticker-based flat candles are attempted. Neither a Coinbase SDK nor an exchange secret is declared. The legacy `lib/api/matches.ts` mentions `/api/market/candles` and legacy match endpoints, but these routes are **not present** in the checked-in `app/api/` tree.
- **Storage:** `app/settings/page.tsx` uploads resized JPEGs to Supabase Storage bucket `avatars`, path `${user.id}/avatar.jpg`, then stores a cache-busted public URL in `profiles.avatar_url`. The bucket setup and `avatar_url` alteration are **not in the checked-in baseline SQL**.
- **Friends/presence:** browser calls `ping_online` RPC; the baseline view `friends_with_status` joins `friends` to `profiles` and derives seconds since last seen. RLS on the underlying relations is material; do not assume the view exposes only the caller's rows solely because a UI comment says so (the baseline view definition has no explicit `f.user_id = auth.uid()` predicate).

### 3.2 Database model as actually represented in checked-in SQL
`supabase/migrations/0000_baseline.sql` is the primary structural reference, with `0001_drop_matches_join_policy.sql` applied conceptually afterward. Relevant table/relationship details:

- **`auth.users`** (Supabase-owned) is the UUID identity referenced by app tables. **`profiles`** has `id` → `auth.users.id` (`ON DELETE CASCADE`), unique `username` and `email`, `created_at`, and `last_seen_at`. Current code reads/writes `profiles.avatar_url`, but the checked-in baseline has no definition of that field; verify live schema independently. Normal users can read all profiles under the baseline `read all profiles` SELECT policy and insert/update their own row; other overlapping own-profile policies exist.
- **`matches`** is both room and match: UUID `id`; `player_one_user_id` required and `player_two_user_id` nullable; status enum `waiting | countdown | active | completed`; `symbol` (baseline default `BTCUSDT`, creation handler uses `BTC/USDT`); `starting_capital numeric`, optional `duration_seconds` and `name`, countdown/start/end timestamps, `final_price`, `winner_user_id` (`null` also means draw), `created_at`. Match player/winner IDs reference `auth.users`. There is no separate `rooms` table, `room_players` table, or DB `cancelled` enum value despite `lib/match/types.ts` including `cancelled` in its TypeScript status union. RLS permits authenticated users to view their own matches **and** waiting matches, insert waiting matches as player one, and delete their own waiting matches. Migration 0001 removes the dangerous join-as-player-two UPDATE policy; the join route instead uses service-role after checking user and conditional update predicates.
- **`match_players`**: UUID ID; unique `(match_id, user_id)` foreign keys to `matches`/`auth.users`; `available_balance numeric`, `realized_pnl numeric`, `current_side` enum `long | short | flat`, `position_notional_usdt numeric`, nullable `average_entry_price`, nullable `final_capital`, nullable `result` constrained to win/loss/draw, `created_at`. The engine creates these rows when a second player has joined and a socket subscriber starts the engine, writes state after accepted orders, writes final state at settlement. Baseline RLS grants a normal user SELECT on **their own** `match_players` rows, not explicitly the opponent's; the engine bypasses RLS. UI code that requests all participants' rows will not necessarily get both in a fresh database using only checked-in policies.
- **`match_candles`**: UUID ID; `(match_id, sequence)` unique, `open_time timestamptz`, numeric OHLC; engine persists one row per streamed tick. Policies include a participant SELECT and an additional authenticated-user SELECT (OR-combined), so effective candle visibility may be broader than the participant-only policy suggests. No `volume` column in baseline.
- **`trades`**: UUID ID; foreign keys to `matches`/`auth.users`; side enum long/short, numeric `amount_usdt`/`execution_price`, optional `candle_sequence`, `executed_at` default now. Current engine inserts **additional fields** `realized_pnl`, `resulting_side`, `resulting_notional`, and live transport queries them, but they are not in this baseline. Trade read policies permit participants to read trades for their matches (and own trades); engine emits each fill privately during the match while history reads both after the fact. No normal-user write policy for trades in baseline. `supabase/mfa-rls-policy.sql` proposes an authenticated-user AAL2 INSERT policy but is an example, not the numbered migration set and not how the service-role engine writes.
- **`friends`**: directed `(user_id, friend_id)` composite PK, references `profiles` with cascades, creation timestamp; normal-user SELECT/INSERT limited to own `user_id` (no friend DELETE policy shown). `friends_with_status` selects friend profile name and `seconds_since_seen` via `last_seen_at`, with `security_invoker=true` but no explicit per-user filter in its SELECT definition; verify actual effective visibility rather than relying on comments. **`public_profiles`** is a separate id/username view (`security_invoker=false` in baseline). **`ping_online()`** updates the calling user's profile `last_seen_at` using `auth.uid()`.

SQL fields with `numeric` are cast using `Number(...)` at multiple JS/TS read boundaries (`lib/match/socket-transport.ts`, history, profile, engine). The engine uses `round2` for some operations; this is **not** an end-to-end arbitrary-precision Decimal implementation. No live DB introspection was performed. Avoid presenting baseline/schema-code mismatches as proof of a deployed failure; document them as unverified dependencies.

### 3.3 End-to-end data lifecycle: from visitor to completed match
**A. Entry and identity (HTTP → browser/server Supabase → redirect):**

1. Browser requests `/` or another non-public path. `proxy.ts`'s Next.js `proxy` matches everything except listed static image/Next assets and `/auth/callback`; it creates a cookie-aware Supabase server client, calls `auth.getUser()`, copies any refreshed auth cookies/headers to the response, and redirects unauthenticated requests to `/login`. Public path list contains `/login`, `/terms-services`, `/privacy-policy`, `/auth/callback`; `/auth/verify-mfa` is **not** public, but an AAL1 user remains signed in while completing second factor. The proxy itself does not require AAL2. Some server pages (`app/page.tsx`, `app/matches/[matchId]/page.tsx`, history detail, profile, leaderboard) also call `getUser()` explicitly; security must not depend solely on client navigation.
2. `/login` creates a browser Supabase client. Registration calls `auth.signUp({ email, password, options: { data: { username } })`, attempts to upsert `profiles` (`id`, `email`, `username`), then navigates to a validated internal `next` route; the profile-upsert return error is **not checked**. Password login uses `signInWithPassword`, checks `mfa.getAuthenticatorAssuranceLevel()`, and, if `aal1 → aal2`, routes to `/auth/verify-mfa`. Google login uses `signInWithOAuth({provider:"google", redirectTo: .../auth/callback?next=...})`; callback exchanges code for cookie session, refetches user factors with the access token, inspects JWT AAL, and routes a verified-factor AAL1 user to MFA; otherwise redirects to the safe destination. MFA page calls `listFactors` and `challenge`/`verify`. `lib/auth/mfa.ts` offers explicit guards, but do **not** assume every game route invokes `requireAuthWithMfa`—the only demonstrated AAL2-protected API is `/api/user/security`.
3. Once authenticated, root `app/page.tsx` renders `SideNav` + `LobbyScreen`. `SideNav` fetches profile username/avatar in the browser and starts `useOnlinePing`: `supabase.rpc("ping_online")` initially and every five seconds when visible, plus a visibility-change refresh. The locale cookie flows through `i18n/request.ts` → `app/layout.tsx` → translation provider; `app/settings/page.tsx` can change it and reload.

**B. Room discovery/creation (React fetch → route handler → RLS-governed Postgres → JSON):**

4. `LobbyScreen` calls `GET /api/rooms` on mount and on manual Refresh (**no automatic five-second room polling in this implementation**, despite PRD recommendation). The route authenticates with `createSupabaseServerClient().auth.getUser()`, reads `matches` rows with `status='waiting'` ordered newest, fetches creator `profiles` (username/avatar), formats age/capital/duration/name with `formatRoom`, puts the current user's room first, and additionally searches for that user's most recent `countdown`/`active` match via `findActiveMatch`. It responds `{ rooms, activeMatch }`; UI renders room cards and a rejoin banner. Data is returned through Next HTTP and Supabase PostgREST, not through Socket.IO for the lobby.
5. `CreateMatchModal` submits `POST /api/rooms` with optional name, chosen capital and fixed 60-second duration. Handler parses JSON; restricts capital to `5000/10000/20000`, limits name to 40 characters, defaults invalid duration to 60, fixes symbol to `BTC/USDT`, authenticates, checks for another non-completed match, then uses the **user-scoped** Supabase client to insert `matches` with creator as `player_one_user_id`, `player_two_user_id=null`, `status='waiting'`. Insert/uniqueness errors return JSON and appropriate 4xx/5xx; success is `201 { room }`. Browser navigates straight to `/matches/<new id>`; no extra creator join. For own waiting room, the lobby's Enter simply navigates to this same URL. Owner deletion is `DELETE /api/rooms` with `{roomId}`, constrained to that owner's waiting row and returns `{roomId}`.
6. Another user presses Join; `LobbyScreen` sends `{roomId}` to `POST /api/rooms/join`. Handler validates JSON/identity, fetches waiting `matches` row through the user-scoped client, rejects own room/full room/concurrent game, computes `countdown_starts_at=now`, `starts_at=now+10s`, `ends_at=starts_at+duration_seconds` (60-second default), then uses `createSupabaseAdminClient()` to update the same `matches` row **only if** it remains waiting and player two remains null. This conditional update prevents two joiners claiming the same second seat; zero updated rows return 409. Success `{roomId}` sends joiner to `/matches/<same id>`. This route does not create `match_players`: socket server creates/loads them later. The `matches` UPDATE uses privileged credentials because regular users have no match UPDATE policy after migration 0001.

**C. Match opening/realtime bootstrap (server page → browser Supabase snapshot → authenticated socket):**

7. `app/matches/[matchId]/page.tsx` awaits async route `params`, checks user, and passes `matchId` to `MatchScreen`. `MatchTransportProvider` supplies `createSocketTransport()` to `useMatchConnection`; the latter owns React state for connection, match/players/candles/trades/price, pending trade, feedback, final result and clock offset. It delegates network operations to `lib/match/socket-transport.ts`, **not** `lib/api/matches.ts`.
8. The transport's `loadSnapshot()` uses the browser Supabase client to `getUser()`, obtains an access token with `getSession()`, reads `matches` and both `profiles`, prior `match_candles` ordered by sequence, the **viewer’s own** `trades`, and their `match_players` row. It converts Postgres numeric values to JS numbers, deduplicates/sorts candles by `time`, derives latest price and a fresh-capital position if the engine has not created player rows, and dispatches a `MatchSnapshot` to the hook. A `match_players` row is read only for self; opponent capital initially defaults to starting capital until the server sends `match:capitals`. Snapshot `serverTime` is local `Date.now()` (tick times subsequently come from the socket). Current browser query errors are often not surfaced explicitly; an absent match yields a disconnected state.
9. `openSocket()` calls Socket.IO `io(NEXT_PUBLIC_SOCKET_URL, { auth: callbackReturningToken })`. On connect/reconnect it emits `match:join {matchId}`. Engine `io.use` validates that access token via Supabase `auth.getUser(token)` and binds the verified `socket.data.userId`; `match:join` looks up the row with service-role Supabase, checks membership, joins Socket.IO room `match:<id>`, then sends `match:waiting`, the saved final result, or starts/joins the in-memory engine and sends own `player:state`/`match:capitals` as appropriate. User IDs supplied inside trade messages are never accepted as identity.
10. When first started for a counting-down/active match, `ensureMatchRunning` loads or inserts two `match_players` rows via service role, constructs an in-memory object with player IDs, epoch start/end, latest price, candle sequence, positions and timer, triggers an asynchronous Coinbase candle prefetch, and sets a **500-ms interval**. One match can be driven by the first participant who joins the socket; creation/join HTTP handlers alone do not start the engine. A `ticking` set suppresses overlapping ticks of the same match. Before start it broadcasts `match:countdown` with seconds left; at start it sets `matches.status='active'`, emits `match:started` and updates counters. UI chooses `WaitingRoom`, `CountdownScreen`, or `ActiveMatch` via `match-screen.tsx`; clock helpers use server timestamp estimates. When status changes from a snapshot missing opponent/clock, the hook can reload its snapshot.

**D. Market/trading (Coinbase → engine → database + socket → React):**

11. Every live tick takes the next prefetched Coinbase one-minute OHLC bar, **replays one bar every 0.5 seconds** regardless of original minute spacing, uses its `close` as tradable price, increments sequence, inserts `match_candles` row with sequence/open_time/OHLC, and emits `match:tick {price,sequence,at,candle}` to both players. If prefetch returned no bars, engine tries Coinbase ticker; successful ticker value becomes a flat fallback candle with incrementing display time. It broadcasts `match:capitals` (both players' mark-to-market equity). The UI transport converts tick format to `lib/match/types.ts` candle format, updates the chart, calculates display-only unrealised PnL/equity from the latest price and own raw position, and sends `onTick`/`onPlayerState` into React. `app/matches/[matchId]/match-chart.tsx` uses `lightweight-charts`; `match-header.tsx`, `position-panel.tsx`, `order-panel.tsx`, and `recent-trades.tsx` present the corresponding view.
12. `OrderPanel` calls hook `submitTrade`, which marks the order pending and emits `trade:submit {matchId, side, amount}` on the live socket. Engine checks that an in-memory match is started/not ended, side is long/short, amount is positive finite, sender's verified user ID is a participant and a price exists. `applyTrade` in `socket/engine-math.js` nets against any opposite exposure, releases/reserves capital and realizes PnL, or returns an insufficiency/error result. On acceptance engine replaces in-memory player, awaits `savePlayer` (`match_players` update) and `saveTrade` (`trades` insert including result fields/candle sequence), emits `trade:accepted` and private `player:state` to the submitting socket, then sends `match:capitals` to the room. On failure it emits `trade:rejected {reason}`. `useMatchConnection` clears pending state and renders fill/rejection feedback; opponents receive capital changes, not private live fill details. Note that `savePlayer`, `saveTrade` and `saveCandle` currently do not inspect Supabase returned errors; awaiting them does **not** prove durable write success, and the SQL baseline lacks some columns they use.

**E. Settlement, history and ancillary reads (engine → Postgres → browser/server UI):**

13. When `now >= endsAt`, engine stops the interval, settles open exposure at the last streamed close with `settlePlayer` (`finalPrice === null` falls back to available balance), compares final capitals, writes each `match_players` final balance/capital/result and sets `matches.status='completed'`, `final_price`, `winner_user_id` (null for draw). It emits `match:ended {finalCapitals,winnerUserId,finalPrice}` to both players and removes the finished in-memory match after 60 seconds. When reconnecting to a completed match the socket service reads persisted final rows instead of re-running the game. `match-screen.tsx` displays the final result/panel, disables active order placement, and offers history/friend navigation. `use-completed-result.ts` is an additional direct Supabase read of saved match/player result for completed view; with the baseline own-only player RLS policy its opponent lookup may be unavailable.
14. `app/history/page.tsx` directly queries completed `matches` for the viewer, `match_players` and `profiles` for summary/stats, then on accordion expansion fetches that match's `matches`, `match_players`, `trades`, `match_candles`, `profiles` and draws a local SVG candlestick chart with both players' trade markers. `app/history/[matchId]/page.tsx` performs its own server-side versions of those reads and renders separate detail/graph; it redirects to `/history` on an unreadable match. Profile queries own completed match wins/losses/draws; leaderboard queries profiles plus completed matches through a user-scoped server Supabase client. Since RLS allows normal users only their own non-waiting matches, leaderboard aggregates may be incomplete for other users under baseline policies. The history UI also requests opponent `match_players`, which own-only RLS may withhold; it contains fallbacks rather than privileged aggregation. No centralized ORM/query service repairs this by default.
15. `AddFriendButton` on the result screen reads/inserts directed `friends` rows via browser Supabase client; friends page polls `friends_with_status` every 5 seconds while visible, computing “online” if `seconds_since_seen < 10`; navigation shell sends heartbeats. Settings performs browser-side profile changes, avatar Storage upload and MFA factor management. These are parallel browser→Supabase data flows, not Socket.IO match operations.
16. On game-server boot, `closeStaleMatches()` marks overdue non-completed matches completed and marks waiting rooms older than one hour completed, allowing blocked users to create/join again. It does **not** reconstruct their missing trades/settlements or pick a winner. A live match stays in the socket server's memory, so restart recovery and persistent record consistency must be evaluated separately; do not describe the database as a fully replayable source-of-truth engine.

### 3.4 Wire contracts and seams that prevent confusion
- HTTP routes present: `GET|POST|DELETE /api/rooms`, `POST /api/rooms/join`, `GET /api/user/security`, `GET /auth/callback`. Response bodies for rooms are `{rooms,activeMatch}`, `{room}`, `{roomId}` depending on action; errors generally `{error: string}` with 400/401/404/409/500. Static/server pages additionally talk directly to Supabase. There is no current `GET /api/rooms/:id`, `/api/rooms/:id/join`, `/api/matches/:id/trade|me|scores|result`, or `/api/market/candles` implementation even though the older `lib/api/matches.ts` has planned branches for them.
- Socket client → server: handshake `{token}`, `match:join {matchId}`, `trade:submit {matchId,side,amount}`. Server → client: `match:waiting`, `match:countdown {secondsLeft}`, `match:started`, `match:tick {price,sequence,at,candle}`, `match:capitals {capitals,at}`, private `player:state {availableBalance,realizedPnl,side,notional,avgEntry}`, private `trade:accepted {side,amount,price,at,realizedPnl,resultingSide,resultingNotional}` or `trade:rejected {reason}`, `match:ended {finalCapitals,winnerUserId,finalPrice}`, and `error {message}`. Browser adaptation contract lives in `lib/match/{types,transport,socket-transport,match-connection}.ts(x)`; transport has connect/reconnect/close and event callbacks.
- Supabase writes have different privilege levels: user-scoped profile/room creation/owner deletion/friend edits; service-role join conditional update and engine game-state writes. Baseline RLS forbids ordinary user match state updates after migration 0001; `supabase/mfa-rls-policy.sql` is illustrative, not proof that the engine requires MFA to place a trade. The room/match status and players must be fetched across both HTTP/DB and socket layers; an HTTP join JSON response by itself does not guarantee the game engine has connected or that market data has loaded.
- Deliberately separate **design/legacy contracts** (`lib/api/`, the PRD's Prisma/rooms/Binance suggestions) from the **current production-shaped source path** (`app/api/rooms`, `lib/match/`, `socket/`, SQL baseline). Sections 4–6 will audit each feature's operational completeness, explicit guardrails, latest changes, defects and planned work rather than treating all checked-in files as active runtime paths.

## 5. ARCHITECTURAL PRINCIPLES & GUARDRAILS

### 5.1 Enforced standards
- **TypeScript strictness:** `tsconfig.json` has `strict: true`, `noEmit: true`, `moduleResolution: bundler`, path alias `@/*` → repo root. New web code should be typed TS/TSX; the socket service is intentionally plain CommonJS JavaScript and should stay that way unless a deliberate refactor is agreed.
- **ESLint:** flat config `eslint.config.mjs` extends Next core-web-vitals + TypeScript. Verification command for this repo: `pnpm run lint` (note: it currently exits 1 — see 6.2).
- **Component conventions:** Next.js App Router with RSC by default; `"use client"` only where interactivity demands it (login, lobby controls, match screen, friends, settings). Server pages fetch their own data with the cookie-backed server client; browser components use the browser client. Route handlers in `app/api/**/route.ts` return JSON `{error: string}` with 400/401/404/409/500 semantics.
- **Naming/structure:** kebab-case filenames, `use-*` prefix for hooks, `page.tsx`/`route.ts` Next conventions; shared UI primitives in `app/components/duel/`; match-domain types centralized in `lib/match/types.ts`; match duration/capital constants centralized in `lib/match/rules.ts` so lobby and match can never disagree.
- **Security invariants (treat as hard rules):**
  1. Never trust client-supplied user IDs. The engine binds identity from the socket handshake token via `supabase.auth.getUser(token)` and ignores any userId in trade payloads.
  2. The engine and the room-join conditional UPDATE use the **service-role** client server-side only (`lib/supabase/admin.ts`, `socket/server.js`). `SUPABASE_SERVICE_ROLE_KEY` must never reach the browser or docs.
  3. Ordinary users have no UPDATE policy on `matches` (removed by migration 0001 after the original join-as-player-two UPDATE policy was found unsafe). Do not re-add broad match UPDATE policies; keep privileged transitions in server code with explicit predicates.
  4. Auth redirects must pass through `lib/auth/redirect.ts` validation (no open redirects).
  5. Don't copy `.env.local` values into code, docs, or commits.

### 5.2 State-management patterns
- **Two state planes:** durable state lives in Postgres (`matches`, `match_players`, `match_candles`, `trades`); ephemeral live-match state lives in the engine's `liveMatches` map. The engine is authoritative for fills and settlement; the browser only mirrors display values.
- **Client match state:** owned by a single hook (`useMatchConnection`) fed by a transport adapter (`MatchTransport` interface in `lib/match/transport.ts`). Components receive props/callbacks; they do not open sockets themselves. Reconnection = new socket + fresh `loadSnapshot()` from Supabase.
- **No global state library:** no Redux/Zustand/React Query. Data fetching is direct Supabase client calls in pages/components plus `fetch` against internal route handlers for rooms. Keep it that way unless the team decides otherwise explicitly.
- **Server-generated UI:** profile/history-detail/leaderboard render server-side; history list, friends, settings are client-side with polling where needed (5 s cadence is the de facto polling standard).

### 5.3 Anti-patterns and things to avoid
- **Do not** build new features on `lib/api/` (mock-defaulted legacy seam). Use `app/api/rooms` + `lib/match/` + Socket.IO.
- **Do not** conflate PRD proposals with implementation: no Prisma, no separate `rooms` table, no Binance, no 180-second matches, no `/rooms/[roomId]` route. Match reality first; update docs deliberately if the design changes.
- **Do not** assume awaited Supabase writes succeeded: `savePlayer`/`saveTrade`/`saveCandle` ignore returned errors today — new persistence code should check results, and fixes should propagate.
- **Do not** add client-writable paths to server-owned match state (status, prices, results, opponent rows) — RLS + service-role separation is the current safety model.
- **Do not** introduce heavy new dependencies (state managers, CSS frameworks, chart libs beyond `lightweight-charts`, ORMs) without an explicit decision; the stack is intentionally lean.
- **Money math:** everything is JS `Number` + `round2`. Don't mix in float-laden recomputes on the client for authoritative purposes; the client mirror is display-only.
